# تصميم: ربط المشروعات الفرعية بالسنوات المالية مباشرة، وتحويل الخطة لأرشيف

**التاريخ:** 2026-07-24
**الحالة:** معتمد (Approved) — جاهز لكتابة خطة التنفيذ
**النطاق:** Backend فقط. الواجهة الأمامية تُبنى في مرحلة لاحقة منفصلة (بعد استقرار كل الـ API).

## السياق

النظام الحالي (SmartInvest) فيه مشروع (Plan) مرتبط بسنة مالية واحدة (Plan.FinancialYearId)، والمشروعات الفرعية بتنضم للخطة عن طريق PlanProject (Plan↔SubProject join)، وده اللي بيحدد تبعية المشروع لسنة مالية بشكل غير مباشر. المشكلة: مشروع ممكن يمتد لأكتر من سنة مالية واحدة، والموديل الحالي مبيسمحش بده (لازم مشروع فرعي واحد يبقى تابع لخطة واحدة بس، وكل خطة مرتبطة بسنة واحدة).

**ملاحظة مهمة:** سلسلة `Plan`/`PlanProject`/`FinancialYear`/`ProjectFollowUp` كلها كيانات موجودة في قاعدة البيانات من البداية، لكن **مفيش أي API (controller/service) اتبنى عليها خالص لحد دلوقتي** — يعني التعديل ده أساسًا بناء جديد على بيانات فاضية، مش تعديل بيانات حقيقية موجودة.

## نظرة عامة على الحل

1. **المشروع الفرعي (`SubProject`) بس هو اللي بيتربط بالسنة المالية مباشرة** (مش المشروع الرئيسي — لأن المشروع الرئيسي مالوش تمويل أو متابعة خاصة بيه، بس بيجمّع مشروعاته الفرعية).
2. **علاقة Many-to-Many** بين `SubProject` و`FinancialYear` عن طريق كيان جديد `SubProjectFinancialYear` — مشروع فرعي واحد ممكن يتربط بأكتر من سنة مالية (مشروع 3 سنين = 3 روابط)، وكل سنة عندها مسار متابعة (`ProjectFollowUp`) مستقل خاص بيها.
3. **الخطة (`Plan`) تبقى أرشيف فقط** — مالهاش أي دور تشغيلي بعد كده (متجيبش الموافقة ولا المتابعة)، بس بتحتفظ بقائمة "لقطة" (snapshot) مجمّدة من المشروعات المقترحة وقت إنشاء الخطة، عشان لو طبعناها بعد كده كمستند تفضل زي ما كانت وقتها بالظبط، حتى لو المشروعات المرتبطة بالسنة اتغيرت بعدين.

## نموذج البيانات

### كيان جديد: `SubProjectFinancialYear`

| الحقل | النوع | ملاحظات |
|---|---|---|
| `SubProjectFinancialYearId` | `int` | PK |
| `SubProjectId` | `int` | FK → `SubProject` |
| `FinancialYearId` | `int` | FK → `FinancialYear` |

قيد فريد على (`SubProjectId`, `FinancialYearId`) — نفس المشروع مايتربطش بنفس السنة مرتين.

**مفيش حقل "حالة موافقة" (ApprovalStatus) على المستوى ده** — تم نقاشه وحسمه: الموافقة على المشروع أصلاً موجودة ومتمثلة بـ `SubProjectCode` (لو موجود = معتمد، وده الاتفاق المستخدم بالفعل في الواجهة الأمامية الحالية `kpiApproved = subs().filter(s => !!s.code)`)، وإضافة حالة موافقة تانية مستقلة على مستوى الربط بالسنة هتبقى حالة زيادة محدش هيستخدمها فعليًا.

`ProjectFollowUp` (الكيان الموجود، هيتفعّل لاحقًا في مرحلة "متابعة المشروع" — راجع "خارج النطاق" تحت) هيتربط بالكيان ده بدل `PlanProject`:
- `ProjectFollowUp.PlanProjectId` → يتغيّر لـ `ProjectFollowUp.SubProjectFinancialYearId` (FK جديد لـ `SubProjectFinancialYear`).

### تعديل `PlanProject` — يتقلّص لـ "لقطة" أرشيفية بس

| الحقل | قبل | بعد |
|---|---|---|
| `PlanProjectId` | موجود | يفضل موجود |
| `PlanId` | موجود | يفضل موجود |
| `SubProjectId` | موجود | يفضل موجود |
| `ApprovalStatus` | موجود | **يُحذف** (غير مستخدم في أي كود حاليًا، والموافقة موجودة أصلاً في `SubProjectCode`) |
| `ProjectFollowUps` (collection) | موجود | **يُحذف** (نقل الدور التشغيلي لـ `SubProjectFinancialYear`) |

قيد فريد على (`PlanId`, `SubProjectId`) — نفس المشروع مايتكررش في نفس الخطة.

### تعديل `Plan` — إضافة تاريخي الاقتراح والاعتماد

| الحقل | ملاحظة |
|---|---|
| `PlanId`, `PlanName`, `PlanStatus`, `FinancialYearId`, `FinancialYear` | بدون تغيير |
| `SuggestionDate` (`DateTime`) | **جديد** — تُضبط تلقائيًا وقت إنشاء الخطة |
| `ApprovalDate` (`DateTime?`) | **جديد** — تُضبط وقت اعتماد الخطة (نطاق "الاعتماد" أسفل) |
| `PlanProjects` (collection) | بدون تغيير في الاسم، لكن دلوقتي بتمثل "المشروعات المقترحة" (لقطة أرشيفية) مش تبعية تشغيلية |

`Plan.FinancialYearId` يفضل موجود — مش زيادة، لأنه بيحدد "الخطة دي لسنة إيه" كتصنيف/عنوان للمستند، مستقل عن الروابط التشغيلية الفعلية بين المشروعات والسنوات.

## حذف الكيانات غير المستخدمة (Cleanup)

بالتحقق الفعلي من الكود، لقينا:

1. **`InvestmentProject`** (الكيان + `InvestmentProjectsController` + `InvestmentProjectService`/`IInvestmentProjectService` + `InvestmentProjectDtos.cs` + `MappingProfile.cs` بالكامل) — نموذج كامل موازي (Title/Description/TargetAmount/Sector/Location/Status)، **مفيش أي استخدام ليه في الواجهة الأمامية خالص** (تم التأكد بالبحث في `Frontend/` — صفر نتائج)، من مخلفات مرحلة مبكرة قبل موديل `MainProject`/`SubProject` الحالي. **يُحذف بالكامل.**
2. **`SmartInvest.Domain.Enums.ProjectStatus`** — Enum مكرر الاسم مع الكيان `SmartInvest.Domain.Entities.ProjectStatus` الموجود والمستخدم فعليًا. المستهلك الوحيد له هو `InvestmentProject.Status` (اللي بيتحذف أصلاً). **يُحذف.**
3. **`ApprovalStatus`** على `PlanProject` — راجع أعلاه.

## نطاق الـ API لهذه المرحلة

### `FinancialYear` — CRUD كامل
حقول: `Name`, `StartDate`, `EndDate`, `IsClosed`. إنشاء/تعديل: مدير + موظف التخطيط (`PlanningStaff`). حذف: مدير التخطيط فقط — نفس نمط Phase 1.

### `SubProject` ↔ `FinancialYear` — ربط/فك ربط
Endpoints تحت `/api/subprojects/{id}/financial-years`: عرض قائمة السنوات المرتبطة، إضافة رابط، حذف رابط. إنشاء/حذف: مدير + موظف التخطيط.

### `Plan` — CRUD + إجراء اعتماد
- إنشاء خطة: `PlanName` + `FinancialYearId` → `SuggestionDate` تُضبط تلقائيًا `DateTime.UtcNow`، `PlanStatus` يبدأ "مسودة".
- إضافة/حذف مشروع من قائمة "المقترحة" (`PlanProject` snapshot).
- تعديل بيانات الخطة الأساسية (الاسم مثلاً).
- إجراء "اعتماد" (`Approve`): يضبط `ApprovalDate` + `PlanStatus` = "معتمدة" — **مدير التخطيط فقط** (قرار بمستوى الحذف، يستأهل نفس التقييد).
- حذف خطة: مدير التخطيط فقط.
- إنشاء/تعديل/إضافة-حذف مشروعات مقترحة: مدير + موظف التخطيط.
- `GET` تفصيلي غني بالبيانات (اسم، تاريخ اقتراح، تاريخ اعتماد، حالة، قائمة كاملة بالمشروعات المقترحة وبياناتها الأساسية) — الأساس اللي هيُستخدم لاحقًا للطباعة/PDF.

## خارج النطاق (Out of Scope هنا)

- **CRUD كامل لـ `ProjectFollowUp`** (رفع صور، ملاحظات، نسبة إنجاز، نسبة صرف) — دي مرحلة "متابعة المشروع" المؤجلة من الطلب الأصلي، لسه هتُصمم لوحدها. هنا بس بنعدّل مفتاحها الأجنبي (`SubProjectFinancialYearId`) عشان تبقى جاهزة للمرحلة الجاية، بدون بناء أي controller/service ليها دلوقتي.
- **توليد PDF فعلي** — بيتأجل. بنبني بس الـ endpoint الغني بالبيانات (`GET` تفصيلي للخطة)، وده اللي هيُستخدم لاحقًا (إما من الواجهة الأمامية بطباعة المتصفح، أو من endpoint مخصص للـ PDF في مرحلة لاحقة لو احتجناه فعلاً). إضافة مكتبة PDF دلوقتي سابق لأوانه من غير حاجة فعلية بتستهلكها.
- **الواجهة الأمامية بالكامل** — مؤجلة لمرحلة لاحقة بعد استقرار كل الـ API (المرحلة دي + مرحلة إسناد الجهات/المقاولين السابقة).

## الهجرة (Migration)

بما إن السلسلة دي (`Plan`/`PlanProject`/`FinancialYear`/`ProjectFollowUp`) مفيهاش بيانات حقيقية (مفيش أي كود بيكتب فيها)، الهجرة دي هجرة تصميمية بحتة بدون مخاطر فقدان بيانات:
- حذف جدول `InvestmentProjects`.
- إنشاء جدول `SubProjectFinancialYears`.
- حذف عمود `ApprovalStatus` من `PlanProjects`.
- تعديل `ProjectFollowUps.PlanProjectId` → `SubProjectFinancialYearId` (FK جديد).
- إضافة `SuggestionDate`, `ApprovalDate` لجدول `Plans`.
